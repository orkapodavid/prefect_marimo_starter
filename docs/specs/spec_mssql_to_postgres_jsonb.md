# spec.md — Generic Microsoft SQL Server to PostgreSQL JSONB Migration

## 1. Objective

Migrate data from one Microsoft SQL Server table into one PostgreSQL table with a **simple phase-1 design**:

- Keep only a small set of metadata fields as first-class PostgreSQL columns.
- Store most source/business fields inside a single `jsonb` column.
- Focus on **safe extraction and successful initial migration**, not final schema refinement.
- Make the migration repeatable, auditable, and easy to improve later.

This is a **lift-and-shift data migration**, not a full relational remodel.

---

## 2. Scope

### In scope
- Read one source table from Microsoft SQL Server.
- Inspect the source schema and source rows.
- Create one PostgreSQL target table.
- Map metadata columns directly.
- Pack the remaining source columns into one `payload jsonb` object.
- Load all rows into PostgreSQL.
- Provide a migration script, SQL DDL, config, and basic validation.

### Out of scope
- Full normalization of business columns.
- Advanced CDC / incremental sync.
- Bidirectional sync.
- Trigger-based replication.
- Perfect type fidelity for every SQL Server edge case.
- Performance tuning beyond basic indexes and batch loading.

---

## 3. Core migration design

### 3.1 Target table pattern
The target PostgreSQL table should use this generic pattern:

- `id`: PostgreSQL-generated surrogate key.
- `source_table`: source table name.
- `source_pk`: optional source primary key serialized as text.
- `source_row_index`: optional deterministic row/order key when no single PK exists.
- `created_at`: preserved from source if present.
- `updated_at`: preserved from source if present.
- `created_by`: preserved from source if present.
- `updated_by`: preserved from source if present.
- `payload`: `jsonb` containing all non-metadata source fields.
- `migration_batch_id`: identifier for the migration run.
- `migrated_at`: timestamp when the row was inserted into PostgreSQL.

### 3.2 Metadata fields kept outside JSONB
Treat the following as raw columns when they exist in the source table:

- primary identifier / source key
- created at
- updated at
- created by
- updated by
- optional row index or extraction order field

Everything else should go into `payload jsonb`.

### 3.3 JSONB payload shape
Each migrated row should have a `payload` object like:

```json
{
  "field_a": "value",
  "field_b": 123,
  "field_c": true,
  "field_d": "2025-01-01T12:34:56",
  "field_e": null
}
```

Guidelines:
- Keep original column names unless normalization is explicitly requested.
- Preserve nulls.
- Use JSON-native booleans/numbers where practical.
- Convert unsupported or awkward source values into safe JSON-compatible representations.
- Prefer strings for ambiguous types if fidelity is uncertain.

---

## 4. Assumptions

The implementation should assume:

- Source database is Microsoft SQL Server.
- Target database is PostgreSQL 14+.
- Initial implementation may be written in Python.
- The migration is table-by-table.
- The source may contain nullable columns, inconsistent values, and legacy types.
- The first goal is correctness and recoverability, not perfect elegance.

---

## 5. Technical requirements

### 5.1 Source introspection
The agent should inspect the SQL Server source table before coding the migration:

- schema name
- table name
- columns
- SQL Server data types
- nullability
- primary key or candidate key
- identity/rowversion/computed-column status if relevant

Prefer system-catalog-driven introspection instead of relying only on hand-written mappings.

### 5.2 Target DDL
Generate PostgreSQL DDL for a target table similar to:

```sql
CREATE TABLE IF NOT EXISTS target_schema.target_table (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    source_table text NOT NULL,
    source_pk text NULL,
    source_row_index bigint NULL,
    created_at timestamptz NULL,
    updated_at timestamptz NULL,
    created_by text NULL,
    updated_by text NULL,
    payload jsonb NOT NULL,
    migration_batch_id text NOT NULL,
    migrated_at timestamptz NOT NULL DEFAULT now()
);
```

Also create pragmatic indexes:

```sql
CREATE INDEX IF NOT EXISTS idx_target_table_source_pk
    ON target_schema.target_table (source_pk);

CREATE INDEX IF NOT EXISTS idx_target_table_created_at
    ON target_schema.target_table (created_at);

CREATE INDEX IF NOT EXISTS idx_target_table_updated_at
    ON target_schema.target_table (updated_at);

CREATE INDEX IF NOT EXISTS idx_target_table_payload_gin
    ON target_schema.target_table
    USING gin (payload);
```

Notes:
- Keep indexes minimal in phase 1.
- Do not over-model the target schema yet.

### 5.3 Column mapping rules
The implementation must support a configurable mapping layer.

Example mapping policy:

```yaml
source:
  schema: dbo
  table: ExampleTable

target:
  schema: raw
  table: example_table_raw

metadata_columns:
  source_pk:
    - id
    - record_id
    - uuid
  created_at:
    - created_at
    - created_date
    - createdon
  updated_at:
    - updated_at
    - modified_at
    - modifiedon
  created_by:
    - created_by
    - createdby
  updated_by:
    - updated_by
    - modifiedby

exclude_from_payload:
  - rowversion
  - timestamp
```

Rules:
- Explicit mappings override heuristics.
- Unmapped business columns go into `payload`.
- Excluded technical columns should not be loaded into `payload` unless explicitly requested.

### 5.4 Type handling rules
Apply the following generic rules:

- `int`, `bigint`, `smallint` → JSON number when stored in payload.
- `decimal`, `numeric`, `money` → JSON number when safe; otherwise string.
- `bit` → JSON boolean.
- `nvarchar`, `varchar`, `nchar`, `char`, `text` → JSON string.
- `datetime`, `datetime2`, `smalldatetime`, `date`, `time` → ISO-like string in payload; direct timestamp/date columns for mapped metadata fields.
- `uniqueidentifier` → string.
- `varbinary`, `binary`, `image` → exclude by default or serialize safely if explicitly required.
- `xml` → string unless explicitly transformed.
- `rowversion` / `timestamp` (SQL Server binary version type) → exclude from payload by default unless needed for audit/debug.
- computed columns → exclude by default unless explicitly requested.

When fidelity is unclear, prefer:
1. successful migration,
2. stable serialization,
3. auditability.

### 5.5 Extraction strategy
The migration should:

- Read source rows in batches.
- Use deterministic ordering when possible.
- Support full-table extraction.
- Avoid loading the whole table into memory at once.
- Log row counts and batch progress.

### 5.6 Load strategy
The migration should:

- Write transformed rows into PostgreSQL in batches.
- Prefer bulk-friendly insert/load methods.
- Be safe to rerun.
- Support either:
  - truncate-and-reload for first-pass migrations, or
  - idempotent upsert/reload behavior keyed by `source_pk` when available.

### 5.7 Idempotency
At minimum, support one of these patterns:

#### Option A — truncate and reload
Good for early testing and small/medium tables.

#### Option B — delete by migration scope and reload
Example:
- delete all rows for a given `source_table`
- reload the current snapshot

#### Option C — upsert by source key
Preferred when a reliable source key exists.

The chosen strategy must be explicit in config and documented.

## 6. Validation requirements

The migration must include simple validation:

- source row count
- target row count
- count of rows with null `payload`
- count of rows missing expected metadata fields
- optional spot-check samples comparing source row vs transformed row

Minimum acceptance checks:
- migrated row count matches expected row count
- all inserted rows have non-null `payload`
- metadata columns are populated when source columns exist
- rerunning the migration behaves according to the selected idempotency strategy

---

## 7. Logging and observability

The implementation must log:

- start/end of migration
- source table and target table
- selected metadata mappings
- batch sizes
- rows extracted
- rows transformed
- rows loaded
- errors with enough context to debug failed rows when practical
- migration batch ID

The logs should be human-readable first; fancy observability can come later.

---

## 8. Error handling

Handle errors pragmatically:

- fail fast on connection/config/schema errors
- surface column/type mapping errors clearly
- optionally capture failed rows into a dead-letter JSONL/CSV file for inspection
- avoid silently dropping columns or rows

If a row cannot be represented perfectly, prefer serializing it safely rather than crashing the entire migration, unless strict mode is enabled.

## 9. Deliverables expected from the LLM agent

The agent should produce:

1. `README.md` with setup and usage
2. migration config file (`yaml` or `.env` + config module)
3. SQL Server introspection SQL
4. PostgreSQL DDL for the target table and indexes
5. migration script in Python
6. validation script or validation commands
7. sample command lines for dry run and real run
8. notes on known limitations / future improvements

## 11. Implementation guidance for the agent

Use Python and keep the solution boring and maintainable.

Suggested approach:
- SQL Server connectivity via a standard Python driver.
- PostgreSQL connectivity via a standard Python driver.
- Use server/catalog introspection to discover the source schema.
- Transform each row into:
  - top-level metadata fields
  - `payload` JSON object
- Load into PostgreSQL in batches.
- Keep business logic minimal and configurable.

Do not over-engineer phase 1.

---

## 12. Non-goals for phase 1

Do **not** spend time on:

- perfect relational target modeling
- advanced partitioning
- CDC streaming
- complex conflict resolution
- UI/dashboard work
- automatic schema evolution for every edge case
- premature micro-optimizations

The objective is to get the data across safely first.

---

## 13. Future enhancements (not required now)

Possible phase-2 improvements:

- split selected high-value fields out of `payload`
- add functional indexes on specific JSONB paths
- add table-specific normalization rules
- add change tracking / incremental sync
- add data quality reports
- add reconciliation reports
- add per-table schema contracts

---

## 14. Final instruction to the implementing agent

Build a **working first-pass migration** that is:

- easy to read
- easy to rerun
- easy to debug
- conservative with data loss
- optimized for correctness over elegance

When a design decision is unclear, prefer the simplest option that preserves source data and keeps the migration moving.
